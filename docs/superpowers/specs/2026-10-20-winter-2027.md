# GooseGrade Winter 2027 refresh design

Date: October 20, 2026. Status: proposed design for review.

## Agreed outcome

Refresh GooseGrade as an anonymous, single-course grade calculator. Make Winter 2027 the default catalog and refresh the homepage, search, course page, and custom calculator. Accounts, saved grades, multi-course dashboards, and cumulative averages are excluded. The older v2 specifications do not authorize those features for this work.

Success means every course in the Winter 2027 source snapshot is discoverable, available grading schemes are tied to their actual term and section, and visitors can calculate grades without altering shared data. Complete catalog coverage does not imply that every outline has been published.

## Approach and alternatives

Recommended: improve the existing Next.js/Supabase application with additive catalog metadata, a staged importer, and a shared single-course calculator. Preserve existing course IDs and historical records. This addresses the verified failures without introducing account infrastructure or replacing hosting.

A data-only refresh would be smaller but would leave the site’s ambiguous term selection and duplicated calculator behavior unresolved. A wholesale replacement of the data model and frontend would create unnecessary migration risk for this scope.

## User experience

- Retain the GooseGrade name and goose mark. Use a warm white background, charcoal text, restrained gold accents, readable headings, and consistent rounded controls. Reduce oversized decorative effects in favor of clear course search and grade entry.
- Homepage: short explanation, prominent course search, visible Winter 2027 term selector, and a secondary link to the custom calculator. Show real catalog and ready-weighting counts only when the data query succeeds.
- Search: support compact and spaced codes, course titles, keyboard selection, loading, failure, and no-result states. Paginate results. Preserve selected term in navigation and shareable URLs. Historical terms remain explicitly selectable.
- Course page: code, title, term, section/outline selector, source link, and weighting availability. Never automatically substitute a historical scheme for a missing Winter 2027 scheme.
- Ready schemes open the calculator. Missing outlines show “Weightings pending”; extracted but unresolved schemes show “Weightings under review.” Both states offer the custom calculator and source access when available. Network failure must not be described as an unpublished outline.
- Calculator: editable assessment names, weights and grades; current average on graded work; completed weight; target grade; required average on remaining weight. Preserve the useful existing add/remove/group/drop/redistribute/reset interactions and provide keyboard/touch alternatives to drag-only actions.
- Changes and entered grades live only in page memory. No account, database write, local-storage persistence, or recovery across reloads. Switching course/term resets calculator state. Clearly identify locally modified schemes and provide reset-to-outline behavior.
- Empty grade inputs are ungraded, while an explicit zero is graded. Do not display a misleading zero average before any work is graded. Invalid inputs and incomplete custom weight totals have actionable messages. A required average above 100 is shown as unattainable under the current scheme; completed courses do not divide by zero.

## Catalog and schema

Keep existing `courses` and `assessments` for outline-specific schemes. Add `course_offerings`, unique by `(code, term_id)`, for the published offering list: course code, listing title, department, term ID/label/start date, source URL, and fetched timestamp. Preserve distinct listing variants such as campus/topic in source metadata; do not infer section identity from them.

This separates “offered this term” from “validated outline available.” Pending offerings have real catalog entries without fake outline URLs or empty schemes presented as ready.

Add backward-compatible scheme metadata to `courses`: validation status, source hash, retrieved timestamp, extraction version, and review reasons. Existing rows start as legacy/unverified; do not label them validated because their weights happen to sum to 100. Retain raw assessment weights separately from effective normalized weights and define group totals consistently. Reconcile the existing live `course_code` column with the committed migrations.

Public access is read-only. Import writes use the existing server-side service-role configuration. Add an atomic replacement RPC with explicit permission restrictions and database-side validation. Inspect deployed SQL types, constraints, and permissions before applying additive migrations. Do not run the database-clearing or fuzzy-cleanup scripts.

## Import flow

1. Fetch the supplied Waterloo list, verify its heading identifies Winter 2027 / `1271`, and stage a dated manifest. Reject empty/malformed responses or unexpected terms. The inspected snapshot has 1,658 unique codes; future legitimate source changes update the count rather than fail a hardcoded assertion.
2. Upsert offering metadata without deleting historical offerings or grading records. Reconcile additions/removals in a report; do not silently delete records missing from one fetch.
3. Search outlines with the configured authenticated session. Follow pagination, require exact course identity or explicit cross-listing evidence, filter to `1271`, and retain all distinct applicable outlines. Validate the term/course again in the fetched source. Fail visibly on expired authentication.
4. Cache fetched sources and hashes in ignored local import artifacts with restricted access. Do not publish authenticated source snapshots; the public UI links to the official outline. Skip unchanged validated extraction results. Never commit cookies or source caches.
5. Extract structured assessment data with schema validation and source evidence for each weight. Use deterministic parsing for clear tables; use the existing OpenAI integration for ambiguous layouts. Do not switch providers or adopt the obsolete v2 infrastructure. Treat outline text as data, not executable instructions.
6. Stage every extraction before writing schemes. Flag missing components, ambiguous groups, duplicate alternatives, nonfinite/negative weights, bonus marks, best-N rules, pass thresholds, and conditional replacement schemes. This release does not introduce a general grading-rules engine; schemes requiring it remain under review rather than being flattened into misleading weights.
7. Normalize only complete, source-supported fixed schemes. Preserve explicitly stated group totals. A difference up to 0.05 percentage points is eligible for rounding correction only when displayed source precision supports that discrepancy; this threshold alone is not validation. Larger differences require source correction/review, never blanket rescaling. Preserve raw values and normalization explanation.
8. Use decimal arithmetic or integer units of 10^-10 percentage points, with deterministic residual allocation within source groups, so persisted accepted fixed-scheme totals equal `100.0000000000`. Preserve explicit zero-weight items and exclude them from weighted denominators.
9. Publish each validated scheme atomically: upsert course metadata and replace/upsert its assessments within one transaction. Preserve stable assessment IDs when reliable source identities exist. Roll back all changes on failure. An unsuccessful refresh must leave the previous valid scheme intact and visibly report its freshness.
10. Resume from manifest checkpoints. Report offered codes, discovered sections, unchanged, published, unavailable, review-needed, blocked and failed separately. Use bounded concurrency, timeouts, backoff, and a small representative trial before full extraction. Record estimated extraction cost before the full paid batch; do not launch an unbounded run.

## Application structure

Share term handling and catalog queries between homepage, header, and course page. Keep data access separate from display components. Extract the duplicated grade calculation and assessment-editing behavior into shared pure helpers and a single calculator component used by course and custom routes. Remove all client attempts to update shared assessments.

Keep the existing routes and historical section links usable. New links include the selected term. Explicit historical section links resolve to their own term with a visible label; conflicting term/section requests produce a clear mismatch state instead of mixing data.

## Verification and release

- Import fixtures: term detection, pagination, exact identity/cross-listing, multiple sections, authentication failure, missing outlines, malformed extraction, conditional schemes, rounding residuals, and idempotent reruns.
- Database integration: restricted write access, uniqueness, rollback after failed replacement, historical preservation, and no ready schemes with empty assessments. Apply against a test database or isolated test records where available; document any test-environment limitation.
- Calculator tests: blanks versus zeroes, partial completion, target calculations, all-complete state, weight redistribution, removed items, explicit zero weights, invalid inputs, and local-only edits.
- UI checks: keyboard search, mobile layout, course/term/section navigation, loading/error/pending/review states, source links, and calculator reset. Run type checks and a production build; visually inspect desktop and mobile layouts.
- Full run audit: every source code appears once in the offering catalog for 1271; all published schemes match their source term; exact decimal totals hold; missing and review-needed schemes are counted honestly. Previously identified Winter 2026 defects are not silently normalized or deleted as part of this refresh.
- Deliver a reviewable branch and preview with migration/import results. Production deployment is a separate final action after the result is available for review. No scheduled automation, new hosting, accounts, or Docker/Kubernetes work is included.
